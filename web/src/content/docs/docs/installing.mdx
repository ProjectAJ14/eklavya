### Where Eklavya runs

Eklavya loads in three places. Two of them are one install; the third is its own.

| Where | How it gets there |
|---|---|
| **Claude Code**, in a terminal | Route A or B below |
| **Claude Code in Claude Desktop** — the Code tab | Nothing extra: it is the same engine reading the same `~/.claude`, so A or B covers it too |
| **Cowork**, in Claude Desktop | [Route D](#d-in-cowork), from Claude Desktop's own Plugins page |

All three write to the same `~/.eklavya/knowledge.db`. You are one learner with
one knowledge graph whichever you are working in, and a concept you were quizzed
on in the terminal comes back for review in Cowork.

Ordinary Claude Desktop **chat** is the exception — chat does not load plugins,
so Eklavya is not there.

Routes A and B are for Claude Code, and they end up in the same place. Pick either.

### A. One command, from a terminal

```bash
npm install -g eklavya && eklavya install
```

That one line gives you both halves: the `eklavya` command on your `PATH`, and
the install it then runs. If you would rather not install anything globally,
`npx eklavya install` does the same setup — but leaves no `eklavya` command
behind, so `eklavya doctor` and `eklavya dashboard` will not exist afterwards.

That does the whole job, in this order:

<Steps>

1. #### Checks your Node version

   Stops with upgrade instructions if it is older than 22, rather than half-installing and failing later. If you need to upgrade first:

   ```bash title="macOS"
   brew install node
   ```

   ```bash title="Windows"
   winget install OpenJS.NodeJS.LTS
   ```

   ```bash title="Linux (nvm)"
   nvm install 22 && nvm use 22
   ```
2. #### Installs the runtime

   The server, the hooks and the SQLite driver go into `~/.eklavya/runtime`. This is the step that downloads the ready-compiled database binary for your platform. It then loads it once to prove it actually works, instead of trusting that `npm` exiting cleanly meant a working binary.
3. #### Installs and enables the plugin

   Copies the plugin into Claude Code's plugin directory and registers it, which is the same end state `/plugin install` produces. If you first added Eklavya with `/plugin marketplace add`, that directory is a git clone rather than a copy — so this fast-forwards it with a pull instead of overwriting it, and says which it did. A clone with uncommitted changes in it is left exactly as it is.
4. #### Installs the chat skill

   A single file at `~/.claude/skills/eklavya/SKILL.md`. It is what lets you change Eklavya by asking in plain English instead of remembering a slash command — [see below](/docs/commands/). It is installed for your user account, not for the plugin, so it keeps working in projects where the plugin is not enabled. If a skill of your own is already at that path, this step says so and leaves it alone.
5. #### Creates the database

   `~/.eklavya/knowledge.db`, migrated and seeded, so `eklavya doctor` works before you have opened Claude Code even once.
6. #### Walks your settings

   Five dials, one step each: `quiz`, `focus`, `cadence`, `difficulty` and `memory`. Each step marks what is set now. Press Enter (or type `next`) to keep it, or type a number or a name to change it. On a first install that is five Enters to the defaults:

   ```text
   2/5  focus  what it teaches
     ▣  1  concept  the transferable idea behind the code
     ◌  2  project  this codebase — the code just written
     ◌  3  learn    a topic you name, taught through your code
     →
   ```

   There is no "already onboarded" state. Every run walks the same steps with your current choices marked, so re-running `eklavya install` is also how you review and tweak them. Answers go to `~/.eklavya/config.json`. The installer never asks about per-project settings; set those with `eklavya config set <key> <value> --project`. Without a terminal, it prints the settings and changes nothing.

   **If you have Claude Mem**, the `memory` step asks a different question. Claude Mem and Eklavya both record every session and recall it at the next one, so with both installed you would get everything twice. If the installer finds Claude Mem (its plugin, or `~/.claude-mem/claude-mem.db`), the step asks which one records:

   ```text
   5/5  memory  Claude Mem is installed too — only one should record
     ▣  1  eklavya     import Claude Mem's history, then uninstall it
     ◌  2  claude-mem  keep it; Eklavya records nothing, quizzes stay on
   ```

   **Eklavya** imports your Claude Mem history, filing each project under its checkout. It works out which checkout from Claude Code's own session transcripts, so you do not have to name them. Then it uninstalls the Claude Mem plugin and moves `~/.claude-mem` to `~/.claude-mem.retired`. Nothing is deleted. **Claude Mem** sets `memory.enabled` to `false`. Questions, levels and the gate work as before. [Moving from Claude Mem](/docs/migrating/) has the details.

   Pass `--memory eklavya` or `--memory claude-mem` to answer that step ahead of time. Without a terminal to ask, the installer picks Claude Mem, because that choice leaves your Claude Mem install and data untouched.

</Steps>

Then restart Claude Code and build something; the questions follow. Running `eklavya install` again is how you upgrade — every step is safe to repeat, and it will not disturb your other plugins or your learning history.

### B. In Claude Code, through the plugin marketplace

If you would rather not touch a terminal:

<Steps>

1. #### Add the marketplace

   ```text
   /plugin marketplace add ProjectAJ14/eklavya
   ```

   A marketplace is a list of plugins Claude Code is allowed to install from. This one points at the Eklavya GitHub repository. You should see a confirmation naming the marketplace `eklavya`.
2. #### Install the plugin

   ```text
   /plugin install eklavya@eklavya
   ```

   The part before the `@` is the plugin, the part after is the marketplace it comes from — they happen to share a name. Claude Code downloads the plugin and registers its MCP server, its six hooks and its eight slash commands.
3. #### Restart Claude Code

   Hooks and MCP servers are wired up when a session starts, so the session you installed from will not have them. Quit and reopen.
4. #### Run first-time setup

   ```text
   /eklavya:setup
   ```

   This checks your prerequisites, creates the database, and asks you two short questions. [The next section walks through it.](/docs/first-run/)

</Steps>

:::note
**What route B does differently.** A slash command cannot run `npm` or write outside the plugin, so this route installs the plugin files but not the runtime and not the chat skill. Your first session starts that download in the background and carries on as normal; the questions begin from the session after it finishes, and the slash commands work throughout. Route A does both up front instead. If you would rather not wait — or you want to change Eklavya by asking rather than by command — run `npx eklavya install` at any point. It finishes the job and is safe to run over an existing install: the plugin files here are a git clone, and it pulls that clone rather than overwriting it.
:::

#### Check that it worked

Run `/plugin` and confirm **eklavya** is listed with no errors. The first thing a healthy session prints is a short banner, like this:

```text title="Session start"
Eklavya active · concept · interleaved · easy (0/100)
Learning 0 · Mastered 0 · Due 0
Dashboard & observations: eklavya dashboard
```

The first line is your dials: focus, cadence, and the level with its runway. Once Eklavya has recalled something for you, a green line joins it — `84% less context from memory reuse`. The counts are this project's, not the size of the shipped catalogue. The last line is dim: while `eklavya dashboard` is running it becomes two links, one to the dashboard and one straight to your observations.

If you see those lines, you are done. If you see nothing at all, jump to [Troubleshooting](/docs/troubleshooting/).

### C. From a checkout (contributors)

Use this when you are changing Eklavya itself and want your edits to take effect immediately.

```bash
git clone https://github.com/ProjectAJ14/eklavya.git
cd eklavya/mcp
npm install        # approve the better-sqlite3 build script if npm asks
npm run build
cd ..
claude --plugin-dir "$(pwd)"
```

`--plugin-dir` tells Claude Code to load the plugin from a folder instead of a marketplace, and sets `CLAUDE_PLUGIN_ROOT` so the MCP server can find itself. Use it rather than relying on the repository's `.mcp.json` as project config, which has no plugin root to expand. The launcher prefers your local `mcp/dist/` build when one exists, so a rebuild is all it takes to see a change.

### D. In Cowork

Cowork keeps its own list of plugins, separate from Claude Code's, so it needs
its own install even if you already have Eklavya in the terminal. It is the same
plugin from the same repository.

<Steps>

1. #### Open the Plugins page

   In Claude Desktop, **Customize** in the sidebar, then **Plugins**.
2. #### Add the marketplace

   **Add marketplace**, then `ProjectAJ14/eklavya`. That is the same GitHub repository route B uses; Cowork accepts the `owner/repo` shorthand or the full `https://github.com/…` URL.
3. #### Install

   Find **Eklavya** in the list and select **Install**. Open it afterwards to see its skills, connector and hooks, which you can switch on and off individually.
4. #### Run first-time setup

   `/eklavya:setup`, the same as anywhere else.

</Steps>

If you would rather not add a marketplace, you can build the package yourself —
`zip -r eklavya.plugin .` from a checkout — and use the upload option on the
same page. The marketplace route is better, because it is the one that gets
updates.

:::note
**What is different in Cowork.** The loop is the same — concepts are logged
while the work happens, questions arrive at the seams — but Cowork produces
documents and analysis rather than code, so Eklavya asks about the work you
produced rather than about a diff. Two things do not carry over:

- **The commit gate does nothing.** It holds `git commit`, and Cowork does not commit. `quiz.enforced` still records the gate and still asks the questions; it just has nothing to block, and says so at session start.
- **Delegated work is not logged.** Cowork does not fire the `SubagentStart` event, so a subagent is never told to log what it exercised. Concepts from the main thread are logged as normal.
- **Questions are signed in the stem.** Cowork draws a question card with no header chip and has no status bar, so the question opens with `[Eklavya]` on its own line instead. The same is true of the Code tab. See [your first session](/docs/first-session/).
:::

### Uninstalling

```bash
npx eklavya uninstall           # removes the plugin and skill, keeps your history
npx eklavya uninstall --purge   # removes ~/.eklavya as well
```

Without `--purge` your knowledge graph stays at `~/.eklavya/knowledge.db`, so reinstalling picks up exactly where you left off. That is deliberate: months of spaced repetition should not disappear because you removed a plugin.

This covers Claude Code and the Code tab in Claude Desktop. Cowork holds its own copy, so remove that one where you installed it — **Customize → Plugins → Eklavya → Uninstall**.

### The `eklavya` command

Some things — checking your setup, serving the dashboard, editing config from a terminal — are done with a small CLI rather than a slash command. Route A above installs it. If you took route B, or used `npx`, add it whenever you want it:

```bash
npm install -g eklavya     # then: eklavya doctor
```

Full list of subcommands: [The `eklavya` CLI](/docs/cli/).

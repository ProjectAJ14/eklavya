# What one real answer history says

**2026-09-06** · `node eval/harness.mjs history` against a single developer's
`~/.eklavya/knowledge.db` · **62 attempts on 56 concepts**, 2026-08-26 to
2026-09-06 · raw numbers in `2026-09-06-history.json`

Read-only, aggregates only: no question or answer text leaves the database.

> **Corrected 2026-09-06, after review.** The first version of this file got
> three things wrong, and two of them were the headline results. The tier table
> counted rows whose outcome predates the `outcome` column as if they were
> answers, which pushed tier 2 below the pass threshold and made tier 1 look
> worst; the decline finding was asserted as settled on evidence covering 2 of
> the 11 rows it was about; and the gap result described decay from a state that
> was never reached. All three are corrected below, with the original claim shown
> so the change is visible. The corrections are less flattering in one place and
> more in another.

## Method

Every attempt Eklavya has ever recorded on this machine, run through
`mcp/src/eval/history-stats.ts`. The repeat check imports `questionFingerprint`
from `store.ts` — the product's own function — so if the product's idea of "the
same question" changes, this measurement changes with it.

## What would make all of this wrong

Before the numbers, because a number that cannot be wrong is not a measurement.

- **The repeat rate is a lower bound, and the error is in the flattering
  direction.** `questionFingerprint` hashes the normalised stem. Two questions
  that ask the identical thing in different words fingerprint differently and
  are **not** counted as a repeat. So this measures *literal* repetition, and
  the promise people actually care about — never being asked the same thing
  twice — is looser than the number suggests. Nothing here bounds the gap.
- **n is one developer, and it is the person who wrote the tool.** Not a sample.
  Someone else's history would differ in every direction at once.
- **62 attempts over 12 days**, and the per-tier cells are 4, 40 and 2. Nothing
  below is significant; the tier-2 row is the only one with enough rows to
  argue about at all.
- **The grader and the question-writer are the same agent.** Grades are assigned
  by the model that wrote the question, immediately after writing it. Mean grade
  is therefore not an independent measure of understanding, and every
  grade-derived number here inherits that.
- **16 of 62 attempts were declines**, excluded from the tier statistics because
  a decline says "not now" rather than "did not know". That is a quarter of the
  data removed by a judgement call, and a different call would move the numbers.
- **18 of 62 predate the `outcome` column**, so for those the answered / blank /
  declined split is genuinely unknown rather than zero. This is not a footnote:
  it is the single biggest source of error in this file, and getting it wrong is
  what the correction notice above is about.
- **`outcome` is supplied by the tutor and validated against nothing.**
  `record_attempt` accepts it as an optional enum and never checks it against
  `answer` or `feedback`, so every outcome-derived number here rests on the
  model having labelled honestly. The decline section below is what that looks
  like when it may not have.

## The promise: never the same question twice

| | |
|---|---|
| Attempts | 62 |
| Attempts that *could* have repeated | **6** |
| Repeats | **0** |
| Of those, ones the product should have caught | 0 |
| Ones older than the 20-attempt window it checks | 0 |

**0 of 6.** Not 0 of 62 — 56 of the 62 attempts were the first question ever
asked about that concept, and a first question cannot repeat. Reporting the
larger denominator would claim 62 opportunities to break the promise where only
six existed.

So the promise held, on six chances. That is the honest strength of this
evidence: it is consistent with the promise being kept perfectly and consistent
with a repeat rate that simply has not had room to show itself yet. The number
becomes worth something at a few hundred attempts, or on a history where
concepts recur.

**Which mechanism would have caught a repeat, corrected.** The first version of
this file credited `hasAskedQuestion` in `store.ts`, which fingerprints the last
20 attempts on a concept. That is the wrong mechanism: it runs inside
`record_attempt`, *after* the question was asked, and it rejects nothing — it
records the attempt and returns `repeat_question: true`. What actually prevents
a repeat is the planner, which fills each item's `asked_before` from
`recentQuestions(db, concept.id, ASKED_HISTORY)` with **`ASKED_HISTORY = 3`**.

So the table now splits three ways, and only the first row is a broken promise:

| | |
|---|---|
| The planner had it in `asked_before` | 0 |
| Only the recorder saw it (distance 4–20), and it does not reject | 0 |
| Outside both windows | 0 |

All zero here, so nothing turns on it — but calling a repeat at distance 4–20
"one the product should have caught" credits a check that never saw it, and the
first version of this file did exactly that.

## Tier calibration: does the ladder mean anything?

**This is where the first version of this file was wrong**, and the error was a
methodological one that flattered nothing and misled anyway.

18 of the 62 attempts predate the `outcome` column. `migrations/004` states the
reader contract explicitly: NULL there means *recorded before this column
existed*, and readers "must treat it as unknown, not as any particular outcome".
The first version excluded declines and silently kept those 18 — 14 of which are
grade 0 — so a grade 0 of unknown provenance was counted as evidence the learner
did not know.

Both readings, because the data cannot choose between them:

| Tier | n | Mean | Pass (≥3) | | n | Mean | Pass (≥3) |
|---|---|---|---|---|---|---|---|
| | **all graded rows** | | | | **known outcomes only** | | |
| 1 (recall) | 4 | 1.00 | 0% | | 2 | 2.00 | 0% |
| 2 (mechanism) | 40 | 2.25 | 45% | | 26 | **3.08** | **61.5%** |
| 3 (judgement) | 2 | 0.50 | 0% | | 0 | — | — |

**The published headline flips.** *"Mean grade at tier 2 is 2.25, against a pass
threshold of 3 — the number least flattering to the tool"* becomes **3.08 and
61.5% passing** once rows of unknown outcome are dropped. So does the other
claim: tier 1 is no longer worst, because both tier-3 attempts turn out to have
unknown outcomes and the row disappears entirely.

Neither reading is the true one. Keeping the rows treats unknowns as failures;
dropping them discards two genuine grade-4 answers along with the rest. What can
be said is narrower and duller than what was published: **on the 26 attempts
whose outcome is actually recorded, tier 2 sits just above the pass threshold**,
and the tier ordering cannot be assessed at all, because tiers 1 and 3 have two
rows and none.

The "definitions may be harder than mechanism for this audience" hypothesis in
the first version rested entirely on the ordering that just vanished. It may
still be true. Nothing here is evidence for it.

## Did anything survive a gap?

**0 of 0**, and the first version's "0 of 1" was measuring the wrong thing.

The single pair it reported was concept 129: a **grade 0** on 27 August and a
grade 2 on 5 September. The file described that as an answer that "did not reach
a pass" nine days later — implying decay from something held. Nothing had been
held. It was two failures nine days apart.

A metric named for what survived a gap now requires that something passed before
the gap. Under that definition this history has **no qualifying pairs at all**:
two gaps exist and both are skipped, because neither earlier attempt passed.

Which is a duller result and the correct one. The tool has not yet produced a
single case of a concept being learned and then re-checked later.

## Outcomes

| | |
|---|---|
| Answered | 28 |
| "I don't know" | **0** |
| Declined | 16 |
| Not recorded (predates the column) | 18 |

**Zero blanks and sixteen declines**, and the declines are where the interesting
result is.

The tool treats the two very differently. A blank is the clearest request for
teaching there is and triggers the explain-then-move-on sequence
`references/grading.md` calls the most important thing in the skill. A decline
means *not now*, and the rule is explicit: record it and **drop it
immediately** — do not ask twice, do not guilt them.

**11 of the 16 declined attempts have tutor feedback stored against them.** A
decline that was dropped immediately has nothing to explain, so feedback on a
declined row is the tutor teaching a concept the developer had just asked it to
leave alone.

Two readings are possible: genuine declines being taught anyway, or blanks being
mis-filed as declines. **The first version of this file claimed the stored
answers settled it. They do not.** The cross-tab is:

| Answer stored | Feedback stored | n |
|---|---|---|
| no | no | 4 |
| no | **yes** | **9** |
| yes | no | 1 |
| yes | yes | 2 |

Only **2 of the 11** lectured rows carry an answer at all. The other **9 have no
answer and full feedback**, which is precisely the shape of a blank that was
taught. So the evidence cited as decisive covered 2 of the 11 rows in question,
and the rival reading is untouched for the other 9.

Worse, the strongest evidence points the other way and the first version cited
it as an *independent* finding: **`dont_know` is zero across all 62 attempts.**
Zero blanks in 62 questions at a mean grade near or below passing is not
plausible. `outcome` is supplied by the tutor and validated against nothing —
`record_attempt` takes it as an optional enum and never cross-checks it against
`answer` or `feedback` — and the tool's own field description says `dont_know`
means "grade 0, outcome dont_know, **after you have taught it**", which
describes exactly a feedback-bearing, answer-less row. A tutor that taught and
then wrote `declined` produces these 9 rows.

One further limit: `feedback` records what the tutor passed to the tool, not
what the developer saw. Nothing in the schema establishes delivery.

Eight of those eleven explanations run over 200 characters, so whichever reading
is right, these are not a stray closing sentence — they are the full teach-it
treatment.

**There is a defect here either way**, which is why it is still the most
actionable thing in this file. Either declines are being lectured, against an
explicit rule, or blanks are being recorded as declines — in which case the
mastery record is wrong for every one of them, the teaching sequence's own
trigger is being lost, and `dont_know` will keep reading as zero forever. The
two need different fixes and this data cannot say which. **What settles it is a
single labelled session**, or a validation in `record_attempt` that refuses a
`declined` row carrying feedback.

The first version also concluded that the teaching sequence "has never run on
this history". That is not supportable: 14 of the 18 unknown-outcome rows are
grade 0 and **all 14 carry feedback**, which is the signature of a blank that
was taught. The sequence may well have run, before the column existed to record
that it did.

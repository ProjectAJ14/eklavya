For the parts of Eklavya that make sense outside a Claude Code session. `npx eklavya install` already puts it on your machine; to have it on your `PATH` permanently use `npm install -g eklavya`, or run any subcommand without installing via `npx eklavya <command>`. The package ships this one command; the MCP server is `eklavya serve`, not a separate executable.

| Command | What it does |
| --- | --- |
| `eklavya serve` | Runs the MCP server on stdio. This is what Claude Code starts for you — you would only run it by hand to point another MCP client at Eklavya. |
| `eklavya install` | Installs Eklavya into Claude Code: checks Node, installs the runtime and its SQLite driver, registers and enables the plugin, installs the two chat skills at `~/.claude/skills/eklavya/` and `~/.claude/skills/eklavya-artifacts/`, and creates the database. Then it walks your settings one step at a time: `quiz`, `focus`, `cadence`, `difficulty`, `memory` — and, when memory is on, which model writes the memories (`providers.observer`: `local`, the default, or a Claude model, `claude-haiku-4-5` recommended). Each step marks the current value and starts the cursor on it: ↑/↓ move, Enter, Space or → choose, a digit jumps. Slow steps show a spinner. The answers are written to the global config. The walk runs on a first install only: once `~/.eklavya/config.json` exists, a later install prints your settings and asks nothing. `--settings` walks them again. If Claude Mem is installed, the memory step asks which of the two keeps recording; `--memory eklavya` or `--memory claude-mem` answers in advance ([details](/docs/migrating/)). Safe to re-run, including for a marketplace install, where it pulls the plugin's git clone forward. `--auto` is the updater's own run: no runtime step and no questions. |
| `eklavya update` | Updates now: asks npm for the latest release, installs it into `~/.eklavya/runtime` if it is newer, then runs the new version's `eklavya install --auto`. You do not need it, because Eklavya already does this in the background at session start, at most once an hour ([Updates](/docs/installing/#updates)). It is the same run, in the open, with the real error when one fails. Never downgrades. |
| `eklavya uninstall [--purge]` | Removes the plugin, the runtime and both chat skills, and deregisters it from Claude Code. Your learning history is kept unless you pass `--purge`, which lists what it deleted. The plugin files and runtime stay while a project-scoped install still uses them, and a git commit gate in the current repository is reported with the command that removes it — see [Uninstalling](/docs/installing/#uninstalling). |
| `eklavya config get` | Prints the effective configuration as JSON, plus the paths of your global file and this project's file under `~/.eklavya/projects/`. If the project file sets `providers`, which only the global file may set, it lists it as ignored. If a config file does not parse, it warns that defaults are standing in for it. |
| `eklavya config set <key> <value>` | Changes one setting. Add `--project` (or its older name `--repo`) to write this codebase's file under `~/.eklavya/projects/` instead of your global config — never into the repository. Add `--topic <topic>` when setting `focus learn`. The previous file is copied to `config.json.eklavya-bak` first, and the file is written readable only by you. A file that does not parse is left alone and the command exits 1, naming it. |
| `eklavya doctor` | Checks that everything is wired up: the runtime, the SQLite driver, the plugin's registration with Claude Code, the chat skill, whether the runtime and plugin versions match, then the database, counts, journal mode, this project's level and runway, the memory queue, and the effective quiz switch, focus and cadence. It also reports a config file that does not parse, and whether the terminal commit gate has the `jq` and `sqlite3` it needs. It also **applies your [concept packs](/docs/packs/)** — the only command that does so unconditionally — and names any that failed to load. Exits non-zero if a check fails, and names the command that repairs it; a broken pack is reported but does not fail the run, because `eklavya install` cannot repair one. |
| `eklavya dashboard [--port <n>] [--no-open]` | Serves your learning history as a local web page and opens it in your browser. `--no-open` serves it and prints the URL instead. See [The dashboard](/docs/dashboard/). |
| `eklavya artifacts <sub>` | Writes and finds the pages under `~/.eklavya/artifacts/`: `new`, `list` and `open`. See [below](#eklavya-artifacts). |
| `eklavya statusline` | Prints your dials as one line for a status bar, or nothing at all. See [below](#eklavya-statusline). |
| `eklavya memory <sub>` | Drives the memory half from a terminal: `status`, `search`, `timeline`, `show`, `replay`, `process`, `stop`, `backlog`, `prune`, `import`, `export`, `restore` and `sync`. See [below](#eklavya-memory). |
| `eklavya db-path` | Prints the database location. Useful in scripts. |
| `eklavya export-rules [--out <file>]` | Writes the tutor pedagogy out as a Markdown rules file, for editors that read one. Claude Code loads the pedagogy in pieces, on demand; a rules file is a single always-applied document, so every piece is inlined into it. With no `--out` it prints to stdout. Nothing in the Claude Code flow needs it. |

### `eklavya memory`

The memory half, for a terminal. Inside a Claude Code session the MCP tools
are better — they scope to the project on their own — but these work anywhere,
and two of them have no equivalent as a tool.

| Subcommand | What it does |
| --- | --- |
| `status` | Is capture healthy: entries, evidence waiting to be summarised, the job queue, why it is paused if it is (not logged in, usage limit, `claude` not found), the worker — its pid, how long it has run, the `claude` pid and the job it is on, and how long ago it last checked in — whether a provider is configured, how many imported Claude Mem entries are filed here and how many sit under names no checkout matches, spool drops, and the reuse totals with the saving or overhead spelled out. This is the command for *"why does Eklavya remember nothing?"* — it tells apart switched off, queued, a provider refusing, and evidence dropped while the database was unreachable. |
| `search <query>` | `--mode keyword\|semantic\|hybrid`, `--limit`, `--all-projects`. Titles and ids, not narratives. |
| `timeline` | Recent entries, newest first. `--limit`, `--since <iso date>`. |
| `show <id>` | One entry in full, with the raw evidence it was built from. |
| `replay` | Backfills memory from this checkout's Claude Code session transcripts: sessions from before you installed Eklavya, and any a hook missed. `--limit <n>`. `doctor` names it as the recovery when events were dropped before they reached the database. |
| `process` | Drains the observation queue now, rather than waiting for the next session seam. `--max <n>`. With a model configured, the hooks already run this in the background at every seam, with `--no-resume` so paused jobs stay paused. It is also the repair for a queue that has **paused**: a provider refusing on auth or quota, or a `claude` the hooks cannot find, parks its jobs rather than spending a dead credential once per tool call, and nothing automatic picks them up again. Running this is how you say you have fixed it — it puts the paused jobs back and says how many. A worker takes four jobs at most; if more are waiting when it finishes, it hands over to a fresh one rather than leaving them for the next session, still one at a time, and never past a paused queue or a job waiting out its retry delay. |
| `stop` | Stops the running worker and the `claude` call it is making. The job it was on goes back to the queue with nothing spent. It only signals processes Eklavya recorded starting — checked by process id *and* start time, so a number the system has since given to something else is left alone. The next session starts a new worker; to keep processing off, set `providers.observer` to `null`. |
| `backlog` | Lists unfinished jobs by project and status, and marks any that came from Eklavya's own summariser sessions — the noise the 1.24.0 bug queued. Then `backlog quarantine`, `backlog discard` or `backlog restore` with a selector: `--helpers`, `--project <key>`, `--session <id>` or `--batch <id>`. Quarantined jobs are kept but never processed until restored; discarded ones are deleted with their raw evidence. A change always needs a selector, because the queue also holds real work. |
| `prune` | Deletes **this project's** raw evidence older than this project's `memory.retention_days`, keeping the observations built from it, along with this project's finished jobs and reuse receipts past the same window. Other projects are untouched, whatever their own setting. Does nothing when retention is unset for this project. The session seams already run this at most every six hours per project, 5,000 events at a time; `prune` runs it now and in full. |
| `import <source.db>` | Imports a Claude Mem database. See below. |
| `export <file>` | A versioned JSON file of entries, tags, evidence links and receipts, readable only by you. It will not replace an existing file unless you add `--force`. |
| `restore <file>` | Reads that file back in. See below. |
| `sync push\|pull\|status` | Exchanges memory with your other devices through a folder they can all see. `--target <dir>` overrides `sync.target`. Memory entries, tags and deletions only — attempts, mastery, gates and receipts never leave. Needs `sync.enabled` and `sync.target`, and does nothing without both; see [Configuration](/docs/configuration/). |

`export` and `restore` are one pair: the file is your backup, and `restore` is
how you undo. Take an export before anything irreversible — an import, a
version upgrade, a `--purge` — and if it goes wrong, restore it.

```bash
eklavya memory export ~/eklavya-backup.json
eklavya memory restore ~/eklavya-backup.json
```

A restore is **additive and idempotent**: it adds what is missing, matches what
is already there by identity rather than by row number, and running it twice
adds nothing the second time. It never writes an attempt, a mastery row or a
gate — restoring memory cannot alter what you have been assessed on. It rebuilds
the search index and the embeddings for everything it brought back, so restored
entries are findable immediately. A file written by a newer version stops with
the version it found and the version this build understands, rather than
guessing at a shape it has never seen.

#### Importing an existing Claude Mem history

```bash
eklavya memory import ~/.claude-mem/claude-mem.db --dry-run
eklavya memory import ~/.claude-mem/claude-mem.db --map-here eklavya
```

The dry run is worth doing first. It opens the source **read-only**, prints the
schema version, the row counts, the projects it found, and a field-by-field
report of what maps where, what is deliberately dropped and why, and which
columns the importer has never seen — and writes nothing.

Three things worth knowing before the real run:

- **It never touches your learning history.** Imported observations arrive
  unassessed. Concepts the source had attached become candidates, not concepts:
  no mastery, no attempts, no gate is affected.
- **It places projects the way `eklavya install` does.** Claude Mem names a
  project with a bare string; Eklavya keys one by the checkout's absolute path.
  The importer reads each project's checkout off Claude Code's session
  transcripts. For one it cannot place, `--map-here <name>` files that source
  project under the checkout you are standing in, and `--map <name>=<path>`
  under any other; a flag beats the transcripts. Anything left unplaced is
  still imported, and still searchable — but only with `--all-projects`, and
  the report says which names those were.
- **It is resumable and it does not duplicate.** Run it twice and the second
  run imports nothing — also from `~/.claude-mem.retired`, where install moves
  the source. `--resume` reuses the snapshot an interrupted run left rather
  than copying the source again.
- **`--verify` checks it row by row.** Every source row is looked up by id in
  Eklavya, missing ones are listed, and each source project shows where its
  entries are filed. It writes nothing, and exits 1 on a gap. A real import
  ends with the same report.
- **A re-run re-homes.** Rows an earlier run left under a bare name move to the
  checkout the map now names, and the report counts them as `re-homed`. That is
  the fix for an import first run without a map.

A source database newer than this importer understands stops with the version
it found and the version supported, rather than guessing at a schema it has
never seen.

### `eklavya artifacts`

The file side of [explainer pages and other artifacts](/docs/commands/#the-artifacts-skill). An agent calls these; you rarely need to.

| Subcommand | What it does |
| --- | --- |
| `eklavya artifacts new <title>` | Starts a page from the Eklavya template under `~/.eklavya/artifacts/<project>/`, named `YYYY-MM-DD-<title-slug>.html` in your local date, and prints its path. The project is the git checkout you run it in — the main checkout, for a worktree — or the directory itself outside one. It never overwrites: the same title twice on one day gets `-2`. `--description <text>` sets the one-line summary, `--kind artifact\|explainer` (default `artifact`) and `--concept <slug>` mark an explainer and link it to its concept, and `--open` opens it in your browser. |
| `eklavya artifacts list [--json]` | Every artifact, newest first, with its path. `--here` narrows it to this project; `--json` prints the rows the dashboard reads, ids included. |
| `eklavya artifacts open <path\|id>` | Opens one in your browser, by its path or by an id from `list --json`. |

### `eklavya statusline`

Your dials, in Claude Code's status bar, so the settings that shape a
question are on screen when it arrives:

```text
~/eklavya · main · Opus 5 · [EKLAVYA concept · interleaved · easy]
```

`eklavya install` sets this up for you, **but only into an empty slot**.
`statusLine` holds one command, so installing ours and keeping yours cannot
both happen, and between the two, yours wins: a status bar is a thing people
build deliberately. If you already have one, nothing is touched and the block
below is the manual route.

```json title="~/.claude/settings.json"
{
  "statusLine": {
    "type": "command",
    "command": "eklavya statusline"
  }
}
```

Already have a status line and want both? Call `eklavya statusline` from your
own script and append the output — it prints one line and exits 0, and prints
nothing when it has nothing to say. An uninstall removes the line only when it
is exactly the one the installer wrote, so a composed one survives.

This is a terminal feature. The Claude Desktop app has no status bar to run it
in, so the dials are not on screen there; questions there are signed with an
`[Eklavya]` line above the stem instead, and [the dashboard](/docs/dashboard/)
carries the settings.

It stays silent when `quiz.enabled` is `false`, when `quiet` is `true`, or when you have
turned Eklavya off for this session, so a bar you have stopped reading is a bar
Eklavya is not writing to. `enforced` is printed in amber, and only appears when
set, because that is
the one dial value with a consequence attached: your commits are gated. Pass
`--no-color`, or set `NO_COLOR`, for plain text.

The bar never shows the tier of the question in front of you. A status bar
refreshes when Claude Code decides to, not when a question appears, so a tier
there would sometimes name the previous question's difficulty. The level is
there instead, and it is the part that explains the pitch — `easy` means tiers
1–2. For the exact tier of any past answer, see [the
dashboard](/docs/dashboard/).

### What `doctor` looks like

```text
$ eklavya doctor

eklavya doctor

  ▣  home        /Users/you/.eklavya
  ▣  runtime     /Users/you/.eklavya/runtime
  ▣  driver      better-sqlite3 loads on Node 22.14.0
  ▣  plugin      /Users/you/.claude/plugins/marketplaces/eklavya — registered, enabled
  ▣  versions    runtime and plugin both 1.25.0
  ▣  skill       /Users/you/.claude/skills/eklavya
  ▣  skill eklavya-artifacts /Users/you/.claude/skills/eklavya-artifacts
  ...
  ▣  concepts    87
  ▣  attempts    41
  ▣  mastered    12
  ▣  journal     wal
  ▣  level       easy (23/100 passing answers in /Users/you/code/api)
  ▣  quiz        on
  ▣  focus       concept
  ▣  cadence     interleaved (one question mid-task, min 4m apart)

▣ ALL CLEAR · Eklavya is wired up
```

This is the first thing to run when something feels wrong.

The checks after `home`, down to `skill`, are the install itself. ▣ is fine, ! wants a look, ◌ is something this command skipped or cannot see, and ▤ is broken. The glyph carries the state on its own, so nothing is lost with colour off (`NO_COLOR`) or in a pipe. They matter because Eklavya fails
quietly by design — every hook exits successfully whatever happens, so it can
never break a session you are in the middle of. The cost of that guarantee is
that a broken install looks exactly like a quiet one: Eklavya simply stops
asking. These checks are the only place that says which it is.

When one fails, `doctor` says so and names the fix:

```text
$ eklavya doctor

eklavya doctor

  ▣  home        /Users/you/.eklavya
  ▣  runtime     /Users/you/.eklavya/runtime
  ▤  driver      FAILED — will not load on Node 24.0.0 — Error: dlopen: symbol not found
  ▣  plugin      /Users/you/.claude/plugins/marketplaces/eklavya — registered, enabled
  ▣  skill       /Users/you/.claude/skills/eklavya
  ...

▤ Something is broken. Run: eklavya install
```

`eklavya install` is the repair for all of them, except a skill of your own sitting at that path. It is idempotent — re-running it
reinstalls the runtime, re-copies the plugin and rewrites the registration,
leaving your learning history untouched. `doctor` never repairs anything itself;
it reports, and you decide.

| Check | What it means when it fails |
|---|---|
| `runtime` | The compiled server is missing from `~/.eklavya/runtime`. Usually an install that was interrupted. |
| `driver` | The SQLite driver will not load — almost always a Node upgrade that left the prebuilt binary on the wrong ABI. |
| `plugin` | The plugin is gone from Claude Code's registry, or is registered but switched off in `settings.json`. |
| `skill` | A chat skill is missing from `~/.claude/skills/eklavya` (or, on the `skill eklavya-artifacts` row, `~/.claude/skills/eklavya-artifacts`). If the name is taken by a skill of your own, `doctor` says so and leaves it alone — move yours first. |
| `updates` | The last automatic update failed; the row gives the reason and when it happened. `eklavya update` retries it and shows the full error, and the last background run is in `~/.eklavya/update.log`. The first line of the row says whether updates are automatic (`auto_update`), the runtime version and the latest one npm reported. This row has its own verdict, `Updates are failing. Run: eklavya update`, because `eklavya install` does not fix it. |
| `versions` | The runtime and the plugin are different versions. Behind: the next session updates the runtime in the background. Ahead: update the plugin with `/plugin update eklavya`, because the runtime is never downgraded. |
| `database` | Says `(created now — it did not exist)` when this run created it. A database that exists but will not open is a failure. |
| `config` | A config file does not parse, so every dial above is a default. Fix the file by hand; `eklavya install` will not touch it. |
| `gate` | The terminal commit gate is installed but `jq` or `sqlite3` is missing, so it lets every commit through. With `quiz.enforced` and no hook installed yet, this is only a warning. |

:::note
**Guard rails you will meet.** `config set` rejects unknown keys and lists the valid ones. `focus learn` without `--topic` is refused outright, because that combination produces no questions at all. `--project` outside a git repository is refused, because there is no checkout to key the settings by.
:::

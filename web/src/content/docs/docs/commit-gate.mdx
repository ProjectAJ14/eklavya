With `quiz.enforced` set, a commit is held until you have answered enough of what this session taught you. Nothing else is blocked — you can still edit, run, test and push.

### What "enough" means, exactly

Each session gets a gate with a **required** number of concepts: how many of the concepts Claude logged while building you have not already mastered, capped at `max_questions_per_task`. The gate opens once you have passed `required × pass_threshold` of them, rounded up — at the defaults, three of four. A concept counts as passed only when it was answered at **grade 3 or better**, and only when this session's work is what put it on the list: a skip counts as answered but never as passed, and a concept a quiz pulled in as review debt cannot clear a bar the diff set, or the gate would be theatre.

`required` is frozen when the gate opens and only ever grows, so mastering concepts mid-quiz cannot shrink the obligation you already have.

While a gate is open, the quiz offers only this session's own work: no review questions from other sessions and no widening to related concepts, since neither could count. That includes a concept you have since mastered in another session — it is still on this session's list, so it is still asked, and the gate can always be passed. It outranks `focus: "learn"` too: a topic answer counts as review rather than work, so while the gate is open the topic waits, and it comes back the moment the gate passes.

### The two paths a commit can take

| Where you commit | What stops it | Installed by |
| --- | --- | --- |
| Inside Claude Code — the CLI or the Code tab in Claude Desktop | A `PreToolUse` hook that inspects every Bash command and denies the ones that are really a `git commit`. | The plugin, automatically. |
| A terminal, or any other editor | A git `pre-commit` hook in the repository. | You, with the script below. |

Install both, or the gate only covers half the ways to commit.

The Claude Code path reads each command the way a shell would, so a commit is caught on its own line after other commands, behind `env`, `sudo`, `timeout` or a `VAR=value` prefix, inside `bash -c "…"`, a subshell or a `$( )`, and as `git -C <dir> commit`. It also holds `git merge --continue`, which runs git's pre-commit hook too. What it cannot see is a git alias (`git ci`), a variable holding the command, or a script on disk that commits. It is a speed bump for an agent that forgot the quiz, not a sandbox. **The git hook is the real enforcement**, because git runs it however the commit was started.

:::note
**Neither path exists in Cowork.** The gate is built on `git commit`, and Cowork
produces documents rather than commits. `quiz.enforced` still applies there in every
other respect — the gate is recorded, the questions are asked, the counts go up
— but nothing is ever blocked, and the session banner says so rather than
leaving you to assume otherwise. If you need enforcement, it has to be on a
surface that commits.
:::

### Installing the git hook

```bash
/path/to/eklavya/scripts/install-git-hook.sh            # in the repo you want gated
/path/to/eklavya/scripts/install-git-hook.sh --uninstall
```

- It needs `jq` and the `sqlite3` command line tool: `brew install jq sqlite` or `sudo apt-get install -y jq sqlite3`. Without them the hook lets every commit through, and `eklavya doctor` flags it on its `gate` row.
- It **chains** to any `pre-commit` hook you already have rather than replacing it — your existing one is moved to `pre-commit.local` and still runs.
- `--uninstall` removes Eklavya's hook and restores the previous one.
- **Running it again upgrades an older hook in place**, and says so.
- It works in a linked `git worktree`: the hook goes into the main repository's hooks folder, which every worktree of it shares.
- If the repository sets `core.hooksPath` — which hook managers such as husky and lefthook do — git never runs the standard hook, so the script installs nothing. It prints the one line to add to the pre-commit hook your manager runs instead, and exits with code 2. That line does nothing if the gate is missing, so it can never block a commit on its own.
- The hook looks for the gate script first in the runtime `eklavya install` keeps current, `~/.eklavya/runtime/node_modules/eklavya/dist/plugin/cli/eklavya-gate`, then at the path you installed it from. If neither exists — after an uninstall, say — the commit goes through with one line on stderr saying it was not gated. A plugin update can never make your commits fail.
- It only acts on projects whose config sets `quiz.enforced` — or the retired `"mode": "enforced"`, which it still reads — so installing it is safe even if you turn enforcement off later. That config is at `~/.eklavya/projects/<checkout>/config.json`, never in the repository.
- It reads **that file and no other** — never your global `~/.eklavya/config.json`. Enforcing globally gates commits made inside Claude Code, but a bare-terminal commit is only held in repositories that say so themselves. A hook installed once must not start blocking because a global setting changed elsewhere. The one thing it takes from the global file is the off switch: if your global config sets `quiz.enabled false` and the project does not turn questions back on, the gate lets the commit through, because nothing would ever ask the questions that pass it.

### What a blocked commit looks like

```bash
  Eklavya is holding this commit.

  You have answered 1 of 4 concepts from this session's work.
  Answering is not the same as passing: a skipped or wrong answer counts here
  but not towards the gate. /eklavya:gate has the passing count.

  Open Claude Code in this repo and run /eklavya:quiz to finish, then commit again.

  To see what is outstanding:  /eklavya:gate
  To turn this off, run: eklavya config set quiz.enforced false --project
```

### How to get through it

<Steps>

1. #### Run `/eklavya:gate`

   See how many concepts are outstanding and what score they need.
2. #### Run `/eklavya:quiz`

   Answer honestly. Guessing does not help — the point is the gap, not the gate.
3. #### Commit again

   Both paths now succeed.

</Steps>

### The safety rules

- **It fails open.** A missing `jq`, a missing `sqlite3`, a missing database or an unreadable config lets the commit through with a warning. A learning tool that bricks commits gets uninstalled.
- **No gate row, no block.** If nothing was taught this session there is nothing to prove, so nothing is held. An unpassable gate teaches nothing.
- **Only opted-in projects are gated.** A project whose config does not set `quiz.enforced` is never touched by the git hook. Because that config is per developer, the gate is something you turn on for yourself — a teammate cloning the same repository is not gated unless they ask for it too.
- **Blanking cannot lock you out.** A grade of 0 never passes, so a session answered entirely with "I don't know" would leave the gate permanently unmet. Once everything else is exhausted, Eklavya re-offers the concepts it taught you, one tier lower and as a different question, until the lesson lands. Concepts you *declined* are not re-offered — the gate holding against a decline is the gate working. The one exception is a decline that came with an explanation anyway: a skip you were taught through was not really a skip, and treating it as one would remove your only way past the gate.

### Does it work in Claude Desktop?

In two of its three places. The **Code** tab runs the same Claude Code engine against the same `~/.claude`, so a normal install covers it with nothing extra to do. **Cowork** works too, but keeps its own plugin list, so install it there as well — [route D](/docs/installing/#d-in-cowork). Ordinary **chat** does not load plugins, so Eklavya is not available in it.

Both surfaces share the one `~/.eklavya/knowledge.db`, so you stay one learner: a concept you met in the terminal on Monday comes back for review in Cowork on Thursday.

### Is Cowork different?

The loop is the same, and the wording adapts. Cowork produces documents and analysis rather than code, so Eklavya asks about the work you produced rather than about a diff. Two things do not carry over: the commit gate has nothing to hold, because Cowork does not commit, and delegated subagents are not asked to log, because Cowork does not fire that event. Both are called out at session start rather than left to surprise you.

### Does anything leave my machine?

Not with the default configuration. The database, the config and the dashboard are all local, the dashboard binds to loopback, and both halves of the product run locally: the summariser that writes observations is extractive and needs no model, and the search index is built by an embedder that runs here. There is no account and no telemetry. The only network access in normal use is npm fetching the server package when you install or upgrade — no learning or memory data is involved. The dashboard makes no request to any other host, fonts included: it uses your system's fonts.

Three settings change that, none of them on unless you turn it on, and each says what leaves before it does:

- `providers.observer` and `providers.embeddings` send captured work to a Claude model so it can write richer observations or better vectors. The model runs through Claude Code (`claude -p`) on your own Claude subscription; there is nothing else to set up. They can only be set in your global config.
- `notifications` sends session wrap-ups to a webhook, a command or a file you name.
- `sync` writes memory entries into a directory you name, for your other machines to read.

An upgrade never enables any of them. If none is configured, the promise above is the whole story.

### Does it remember my code?

It remembers *about* your code. Every tool call is recorded as evidence — what the tool was, the arguments, the files, and the error if it failed — and those are distilled into short observations. It deliberately does not store tool *results*, so a successful `Read` of a file does not put that file in the database; the corpus would otherwise become a second copy of your repository.

Paths that usually hold secrets — `.env` files, `~/.ssh/`, `.pem`, `.npmrc` and others — are never captured at all, and more than a dozen shapes of access key, token, password and private key are redacted before anything is written. [The memory page](/docs/memory/) has the full list and how to add your own.

### Will it slow down my work?

A checkpoint question is one keystroke, asked while Claude is still working. The hooks read SQLite directly rather than going through the MCP server precisely because they sit on the critical path of something you are already doing.

### Can I skip a question?

Always, when quizzing is unenforced. A skip is recorded as a decline: grade 0, excluded from your accuracy, and not re-offered by the commit gate. With `quiz.enforced` you can still skip individual questions, but the gate stays shut until enough concepts are answered.

### I am in the middle of something urgent. Can I turn it off just for now?

Say **"turn Eklavya off for this session"**. The questions go quiet — questions, checkpoints, banner, status bar — until the session ends, and nothing is written to either config file, so tomorrow is configured exactly as today was. `quiz.enabled: false` in a config file is the other way to do it, and the one that is still off next month.

Memory keeps recording either way. There is no session switch for it, deliberately: a day of work nobody recorded is a day nobody can look up later. If you want that stopped too, it is `memory.enabled: false`, and it is a file.

It silences the questions, not the [commit gate](/docs/commit-gate/): in a project running `quiz.enforced` the git hook still holds the commit, because it reads that project's config and has no idea which session you are in.

### Why did it ask about something I already know?

Either it is not yet marked mastered — that needs two repetitions at a decent score — or spaced repetition brought it back for review. A review question is never the same question as last time, and often a tier higher.

### Can my team share settings?

No, and deliberately not. Eklavya writes no configuration into a repository: your settings for a codebase live in *your* home directory, at `~/.eklavya/projects/<checkout>/config.json`.

That is a change from earlier versions, which read a committed `<repo>/.eklavya.json`. Two reasons it went. Everyone on a team is at a different point — the level you have earned in a codebase is not the level a new teammate has — so one committed file could never be right for all of them. And a committed config is a configuration file written by somebody else: a checked-in notification sink pointing at a shell plus the automatic end-of-session wrap-up made cloning a repository and working in it for ten minutes run that command. A repository that still has one cannot do that: those settings are ignored when they come from a checkout, and stripped when the file is moved out.

What a team can still share is a [concept pack](/docs/packs/) at `<repo>/.eklavya/packs/` — the concepts a codebase is about, which genuinely is the same for everyone.

### Can two Claude Code sessions share one quiz?

Yes — one pane building while another teaches, sharing a single database. Set the same `EKLAVYA_SESSION_ID` in both. See `docs/parallel-tutoring.md` in the repository.

### I work in two repositories at once. Will they mix?

No. There is one database for every project, but the session Eklavya files your work under is keyed by repository, so a question asked in one checkout is about that checkout's work. Two sessions in the *same* checkout still share one — that is the mechanism the question above relies on.

### How do I upgrade?

Run `/plugin` and update Eklavya from the menu, or run `eklavya install` again — every step of it is safe to repeat, and it moves the whole install forward: the runtime, the chat skill, the registration, and the plugin files themselves (by pulling the git clone, if you installed through the marketplace). Either way, restart Claude Code afterwards: hooks and MCP servers are wired up when a session starts, so the running one keeps the old build.

### How do I uninstall?

Three independent steps — do as many as you want:

1. Remove the plugin from the `/plugin` menu in Claude Code, or run `npx eklavya uninstall`, which also removes the chat skill from `~/.claude/skills/eklavya/`.
2. Restore your previous git hook: `/path/to/eklavya/scripts/install-git-hook.sh --uninstall`
3. Delete your learning history: `rm -rf ~/.eklavya`

Removing the plugin leaves your history intact, so you can come back to it later.

## Still stuck?

Every default, flag and rule in this manual is written from Eklavya's source. If
the docs and the tool disagree, **the tool is right and the docs are a bug** —
[open an issue](https://github.com/ProjectAJ14/eklavya/issues).

### Where settings live

| Layer | File | Applies to |
| --- | --- | --- |
| Defaults | built in | Everything, until something overrides it. |
| Global | `~/.eklavya/config.json` | You, on every project. |
| Project <Badge text="wins" variant="tip" size="small" /> | `~/.eklavya/projects/<checkout>/config.json` | You, on one codebase. |
| Session <Badge text="quiz only" variant="tip" size="small" /> | no file — held in the database until the session ends | This one session, on any project. |

**Both files are in your home directory.** Nothing Eklavya configures is written into a repository, so your settings never reach your teammates and theirs never reach you — see [below](#nothing-eklavya-configures-lives-in-your-repository).

The project directory is named after the checkout's absolute path with the separators turned into dashes, the way `~/.claude/projects/` names its own:

```text
~/.eklavya/
  config.json                                        you, everywhere
  projects/
    -Users-you-code-api/config.json                  you, on ~/code/api
    -Users-you-code-web/config.json                  you, on ~/code/web
```

A git worktree shares its main checkout's settings — a branch parked in a worktree is the same codebase, not a new one to configure from scratch.

Later layers win key by key, not file by file: a project file setting only `quiz` leaves your personal `focus` alone. Which project you are in is found by walking up from your working directory to the **git root**, so a directory that merely contains a checkout is never mistaken for it. A missing or malformed file is ignored rather than fatal — defaults win and your session keeps working.

### Turning it off for one session

Both files outlive the afternoon that made you want silence, which is how a
"just for now" `quiz.enabled: false` becomes questions you switched off in April
and noticed in June. So there is a third scope that takes `quiz` and nothing
else:

> **"Turn the questions off for this session."**

No questions, no checkpoints, no banner, no status bar, until the session ends —
and nothing on disk changes, so the next session is configured exactly as it was.
Ask for it back in the same words (**"turn Eklavya back on"**) and the session
picks up where it left off; concepts logged while it was silent are not lost,
they stay unmastered and a later session in the same project offers them again once its own work and
review debt are covered.

Two things it deliberately does not do.

**It does not stop memory.** Recording has no session scope at all: a day of work
nobody recorded is a day nobody can look up later, and asking for quiet is not
asking for a hole in your history. If you want the recording stopped too, that is
`memory.enabled: false`, and it is a file.

**It does not open the commit gate.** In a
project running `quiz.enforced`, the [git hook](/docs/commit-gate/) reads that
project's config and has never heard of a session, so a commit still waits for the
quiz — and the gate keeps *growing* while you are silent, because the work still
gets logged and the quiz that would have drained it is the thing you switched
off. Silence an enforced session for an hour and the quiz waiting at `git commit`
is a longer one. Silencing the questions and skipping the gate are different requests, and
only a project or global change to `quiz.enforced` is the second one.

### Every key

| Key | Default | What it does |
| --- | --- | --- |
| `quiz.enabled` | `true` | Whether questions happen at all. `false` stops every question, checkpoint and gate — and stops **nothing else**: memory keeps recording, under `memory.enabled`, and the banner says `memory on · questions off`. |
| `quiz.enforced` | `false` | Whether the session quiz must pass before `git commit` succeeds. Setting it also exempts quizzing from the cooldown and the one-question cap, so the gate stays passable. Ignored when `quiz.enabled` is `false` — a gate nothing asks questions for could never be opened, and `eklavya doctor` reports the contradiction. |
| `mode` <Badge text="retired" variant="caution" size="small" /> | — | The dial `quiz` replaced. Still read wherever it appears, for ever: `ambient` → `{enabled: true, enforced: false}`, `enforced` → `{enabled: true, enforced: true}`, `off` → `{enabled: false}`. A `quiz` in the same file wins over it. Do not write it in new configuration. |
| `focus` | `"concept"` | What it teaches: `concept`, `project`, `learn`. |
| `focus_topic` | `null` | The topic for `learn` focus. Ignored by the other two, required by that one. |
| `cadence` | `"interleaved"` | When it asks, and how many at once: `interleaved` asks mid-task, one question per quiz (`quiz.enforced` and quizzes you ask for excepted); `end` waits and asks the remaining budget. |
| `difficulty` | `"auto"` | The tier band: `auto` earns it per project; `easy`/`medium`/`hard` pin it and stop progression. |
| `level_up_after` | `100` | Passing answers needed at the current band, in one project, before it moves up. Answers earned before a promotion are spent. The distinct-concept floor scales with this, so shortening it keeps the runway reachable. |
| `level_up_accuracy` | `0.7` | Minimum accuracy over every answer at that band, not only the passing ones. Declines are excluded from both halves of the fraction. |
| `pass_threshold` | `0.7` | The fraction of a session's required concepts you must answer correctly — grade 3 or better — before the commit gate opens, rounded up. `required` never exceeds `max_questions_per_task`, so at both defaults that is three of four. |
| `max_questions_per_task` | `4` | A budget for the **whole session**, shared between mid-task checkpoints and the end-of-task sweep. Not a batch size — on the default cadence a quiz asks one question, so the budget is spent one at a time or not at all. |
| `min_minutes_between_quizzes` | `20` | Floor between whole quizzes, and the anti-nagging dial for the `end` cadence. It applies when quizzing is unenforced only — `quiz.enforced` ignores it, or a cooldown could make a commit gate unpassable. On `interleaved` nothing it paces exists: every quiz there is one question, so `min_minutes_between_checkpoints` is the dial that applies. |
| `min_minutes_between_checkpoints` | `4` | Floor between single questions on the `interleaved` cadence — both the mid-task checkpoint and the end-of-task sweep. It is what stops eight logged concepts becoming eight questions in a row, and it is what re-arms both: the checkpoint on Claude's next shell command or edit, the sweep on the next finished turn, so lowering it asks more often and raising it asks less. `0` asks at every seam; the end-of-task sweep still keeps a one-minute floor, since there this clock is its only loop guard. |
| `max_new_concepts_per_session` | `8` | Cap on concepts Claude may invent per session, against slug sprawl. |
| `max_stop_blocks_per_session` | `3` | Hard backstop on how many times the end-of-task hook may hold a session open. |
| `domains_enabled` | `["*"]` | Restrict questions to named domains. `["*"]` means all. |
| `auto_update` | `true` | Eklavya updates itself: at most once an hour, a session start checks npm in the background and installs a newer release ([Updates](/docs/installing/#updates)). `false` stops that, and stops the background catch-up install when the plugin is newer than the runtime; a missing runtime is still installed. `eklavya update` still works by hand. Global only: a project file that sets it is ignored, because there is one runtime per machine. |
| `quiet` | `false` | `true` suppresses the session-start banner and the `eklavya statusline` output. It does **not** stop Eklavya working — concepts are still logged and questions still arrive. Use `quiz.enabled: false` for that. |
| `explain_on_wrong` | `false` | `true` writes you an explainer page each time you miss a question — a wrong answer (grade 1 or 2) or an "I don't know" you were taught, never a skip or a decline. The page is written in the background by the `eklavya-explainer` agent, filed under `~/.eklavya/artifacts/<project>/` and opened in your browser; the quiz gives its verdict and goes back to the task without waiting for it. Usually set per project. Asking "explain this to me" gets a page whether this is on or not. |

### Setting a namespaced key

`eklavya config set` takes a dotted path, and so does asking in chat:

```bash
eklavya config set memory.capture minimal
eklavya config set retrieval.cross_project true
eklavya config set privacy.exclude_paths "/internal/, /vendor/"
eklavya config set providers.observer null
```

Only the key you name changes; the rest of its namespace is left alone. A list
takes either a comma-separated string or JSON, and a value is read as the type
the setting actually has — so `focus_topic 2` stays the string `"2"` while
`memory.batch_max_events 40` becomes the number `40`.

The one thing that needs JSON is setting a whole object, because there is no
sensible shorthand for one:

```bash
eklavya config set providers.observer '{"kind":"anthropic","model":"<model-id>"}'
```

### The memory namespaces

The keys above are flat because every config already written uses them that way. The memory half's keys are nested under six namespaces instead, and they merge the same way: a project file setting `retrieval.mode` leaves your global `memory.capture` alone.

#### `memory`

| Key | Default | What it does |
| --- | --- | --- |
| `memory.enabled` | `true` | Whether this project's work is recorded and recalled at all. |
| `memory.capture` | `"full"` | What the capture path accepts. `full` records prompts, tool calls, failures, edits and reads; `minimal` keeps prompts, assistant messages, session seams and notes, and drops the per-file traffic that is most of the volume; `off` stops capture and leaves what is already stored searchable. |
| `memory.batch_max_events` | `40` | The most events in one observation batch; a batch closes mid-task when it reaches this. The end of a turn closes a smaller one only at 8 events or 20 minutes old, and a session start closes whatever is left, so a short session is still summarised. |
| `memory.retention_days` | `null` | Days of summarised raw evidence to keep. Observations built from it survive its deletion; only their drill-down gets shorter. Finished jobs and reuse receipts older than the window are deleted too. Applies per project: set in a project's config it prunes that project only, and another project's evidence is never touched by it. Runs at a session seam at most every six hours per project, or now with `eklavya memory prune` from inside the project. `null` keeps it all until you delete it. |

:::note
**`memory.enabled` is independent of `quiz`.** `quiz.enabled: false` means no quizzes, no checkpoints and no gate — it does not mean no history. Someone who silenced the questions did not ask for their project's record to stop, and the reverse (quizzes, no capture) is just as legitimate: that is `memory.enabled: false`. This was always how it worked; the settings are named `quiz` and `memory` now so that it is legible from the configuration file rather than only from this paragraph.
:::

#### `privacy`

Every entry here is *added* to Eklavya's built-in rules, never replaces them. [Memory](/docs/memory/#what-is-never-captured) lists what the built-in rules already cover.

| Key | Default | What it does |
| --- | --- | --- |
| `privacy.exclude_paths` | `[]` | Extra path fragments that are never captured, on top of the built-in list (`.env`, `/.ssh/`, `.pem`, `credentials.json` and the rest). Matched as a substring of the path. |
| `privacy.exclude_tools` | `[]` | Tool names never captured, when a tool's arguments are usually secrets. |
| `privacy.redact_patterns` | `[]` | Extra regular expressions, applied on top of the built-in secret shapes. A match becomes `[redacted:configured]`. A pattern that does not compile is skipped rather than breaking capture. |

#### `retrieval`

| Key | Default | What it does |
| --- | --- | --- |
| `retrieval.mode` | `"hybrid"` | How memory is searched: `keyword` (FTS5, BM25), `semantic` (cosine over local vectors), or `hybrid` — both, fused. A single search may override it. |
| `retrieval.max_items` | `6` | Entries offered at a session seam before any detail is fetched, and the default `limit` for a search. |
| `retrieval.max_tokens` | `1200` | Estimated-token budget for the whole recalled block, wrapper included. It fills to the budget rather than to `max_items`, because six short notes and six long ones are not the same amount of context. |
| `retrieval.cross_project` | `false` | `true` widens both search and the session-start block to every project on this machine. Off by default: another repository's work is usually noise. |

#### `providers`

Both are `null`, and **nothing turns them on for you** — not an upgrade, not a command. With them unset, the summariser and the embedder are both local and nothing about your code leaves the machine.

`providers` is **global only**: it can be set in `~/.eklavya/config.json` and nowhere else. One background worker summarises every project's queue on this machine, so a per-project setting would decide what leaves the machine for other projects too. A project file that sets it is ignored, and `eklavya config get` lists it as ignored; `eklavya config set providers.observer … --project` refuses.

| Key | Default | What it does |
| --- | --- | --- |
| `providers.observer` | `null` | A model that writes observation narratives instead of the local extractive summariser. Setting it is the one thing that sends captured work off this machine. |
| `providers.embeddings` | `null` | A model that produces the vectors `semantic` retrieval compares, instead of the local `local-hash-v1` embedder. Each vector records which embedder made it, so two models' vectors are never compared. |

Each takes an object of two fields: `kind` (only `"anthropic"` today) and `model`. The model runs through Claude Code (`claude -p`) on your Claude subscription — the same login Claude Code already uses, and nothing else to configure. `eklavya install` asks for the observer model once memory is on.

```json title="~/.eklavya/config.json"
{
  "providers": {
    "observer": {
      "kind": "anthropic",
      "model": "claude-haiku-4-5"
    }
  }
}
```

### Nothing Eklavya configures lives in your repository

Project settings are **yours**, not your team's. They sit in your home
directory, keyed by the checkout's path, and no Eklavya configuration file is
ever written into a working tree.

That used to be the other way round: settings lived at `<repo>/.eklavya.json`
and were committed, so a lead could pin the gate for everyone who cloned. Two
problems with that, and the second is the serious one. Everyone on a team gets
taught differently — the level you have earned in a codebase is not the level
your new teammate has — so one file could never be right for all of them. And
a committed config is a configuration file **written by somebody else**: a
checked-in `notifications` sink pointing at `/bin/sh` plus the automatic
end-of-session wrap-up meant that cloning a repository and working in it for
ten minutes ran that command. Containing this needed a list of settings a
repository was not allowed to touch.

Moving the file out removes the class where it was worst. `notifications`,
`sync` and `retrieval.cross_project` are ordinary settings you can now set per
project, because a file under your home directory is one only you wrote.
`providers` is the exception, and global only, for the reason above.

The restriction survives in exactly one place: a **legacy `.eklavya.json` still
sitting in a checkout**. That file did arrive by clone, and it applies until a
session moves it, so those four settings are ignored when they come from it and
are stripped rather than carried across when it is moved. A repository cannot
hand you a notification sink, before or after the migration.

:::note
**An `.eklavya.json` left in a checkout is moved for you.** The next session
that starts there lifts it into `~/.eklavya/projects/` and deletes it from the
working tree, keeping every setting it held. Nothing is printed and nothing is
asked — a settings file in a repository was a mistake to undo, not a decision
to confirm. If project settings already exist, they win and the old file's
extra keys are merged underneath them, so nothing is lost either way.

Concept packs are the deliberate exception and still live at
`<repo>/.eklavya/packs/`. A pack is a shared concept graph for the codebase,
the same for everyone by design — content rather than configuration. See
[Packs](/docs/packs/).
:::

#### `notifications` — what gets sent out

Off by default, and separately from everything else, because a notification
cannot be recalled: once a session summary is in a team channel, deleting your
local database changes nothing.

| Key | Default | What it does |
| --- | --- | --- |
| `notifications.enabled` | `false` | The master switch. With no sinks configured nothing is sent either way. |
| `notifications.sinks` | `[]` | Where wrap-ups go. Each is an object: `kind` (`"webhook"`, `"command"` or `"file"`), `target`, optional `args` (for `command`), and optional `events` to take only some kinds. |

Two event kinds today: `session_summary` when a session ends, and
`queue_paused` when observation processing has stopped and will not restart by
itself. Every payload goes through the same redaction as capture, and each
event is delivered once however many times the session seam fires. All sinks
share a five-second budget at the end of a turn; a slow one is not waited on
past that.

`command` exists because the interesting integrations are all somebody's
script — a desktop notification, a line in a journal, a message posted by a CLI
that already holds the credentials. The event JSON arrives on the command's
standard input, and no shell is involved, so nothing in `target` is expanded on
the way.

```json title="~/.eklavya/config.json"
{
  "notifications": {
    "enabled": true,
    "sinks": [
      { "kind": "file", "target": "~/eklavya-wrapups.jsonl" },
      { "kind": "command", "target": "/usr/local/bin/notify-me", "events": ["queue_paused"] }
    ]
  }
}
```

#### `sync` — memory across your machines

Off by default. The target is a directory both machines can see — a synced
folder, a mounted share, a git repository — so there is no account and no
service to depend on.

| Key | Default | What it does |
| --- | --- | --- |
| `sync.enabled` | `false` | The master switch. A target alone does nothing, deliberately: a stale path left by a wiped machine should not quietly start publishing. |
| `sync.target` | `null` | The shared directory. Each machine writes its own numbered records into it and reads the others'. |
| `sync.device_id` | `null` | Pin this machine's identity. Normally leave it: an id is minted once and kept in the database, never in a config file, because config files travel and two machines sharing an id would interleave one stream irrecoverably. |

What crosses: memory entries, their tags, and deletions. What never crosses:
your attempts, your mastery, your review schedule, gates, reuse receipts, and
the raw evidence behind an observation. Shared project memory is not shared
learner history.

```bash
eklavya config set sync.target ~/Dropbox/eklavya-sync
eklavya config set sync.enabled true
eklavya memory sync push
eklavya memory sync status
```

Two machines editing the same entry between syncs is a conflict, and a
conflict is **quarantined rather than merged**: your local version stays live,
the incoming one is kept intact, and `eklavya memory sync status` says there is
one to resolve. A deletion propagates as a tombstone and stays deleted — the
machine that still had the entry cannot put it back.

### A complete file

Every key is optional — write only the ones you want to change. This example is a project file for a codebase you are new to: gated, grounded in the project, held at easy.

```json title="~/.eklavya/projects/-Users-you-code-api/config.json"
{
  "quiz": { "enabled": true, "enforced": true },
  "focus": "project",
  "cadence": "interleaved",
  "difficulty": "easy",
  "pass_threshold": 0.7,
  "max_questions_per_task": 4,
  "min_minutes_between_checkpoints": 4
}
```

:::tip
**Two settings people misread.** `max_questions_per_task` is a session budget, so turning on `interleaved` moves questions earlier without adding any — and under that cadence it is a ceiling for the session, not a number of questions you will be asked. And `difficulty` is a *band*, not a question — pinning `hard` does not make every question tier 5, it makes tiers 3–5 the range the planner may choose from.
:::

### Where settings live

| Layer | File | Applies to |
| --- | --- | --- |
| Defaults | built in | Everything, until something overrides it. |
| Global | `~/.eklavya/config.json` | You, on every project. |
| Repo <Badge text="wins" variant="tip" size="small" /> | `.eklavya.json` at a repository root | Everyone working in that project. |
| Session <Badge text="mode only" variant="tip" size="small" /> | no file — held in the database until the session ends | This one session, on any project. |

Later layers win key by key, not file by file: a repo file setting only `mode` leaves your personal `focus` alone. The search for a repo file walks up from your working directory and **stops at the git root** (or at your home directory, whichever comes first), so a stray config above the repository never leaks in. A missing or malformed file is ignored rather than fatal — defaults win and your session keeps working.

### Turning it off for one session

Both files outlive the afternoon that made you want silence, which is how a
"just for now" `mode: off` becomes a tool you turned off in April and noticed in
June. So there is a third scope that takes `mode` and nothing else:

> **"Turn Eklavya off for this session."**

No questions, no checkpoints, no banner, no status bar, until the session ends —
and nothing on disk changes, so the next session is configured exactly as it was.
Ask for it back in the same words (**"turn Eklavya back on"**) and the session
picks up where it left off; concepts logged while it was silent are not lost,
they stay unmastered and a later session offers them again once its own work and
review debt are covered.

One thing it deliberately does not do: **it does not open the commit gate.** In a
repo running `enforced` mode, the [git hook](/docs/commit-gate/) reads
`.eklavya.json` and has never heard of a session, so a commit still waits for the
quiz — and the gate keeps *growing* while you are silent, because the work still
gets logged and the quiz that would have drained it is the thing you switched
off. Silence an enforced session for an hour and the quiz waiting at `git commit`
is a longer one. Silencing the questions and skipping the gate are different requests, and
only a repo or global `mode` change is the second one.

### Every key

| Key | Default | What it does |
| --- | --- | --- |
| `mode` | `"ambient"` | How hard Eklavya pushes: `ambient`, `enforced`, `off`. |
| `focus` | `"concept"` | What it teaches: `concept`, `project`, `learn`. |
| `focus_topic` | `null` | The topic for `learn` focus. Ignored by the other two, required by that one. |
| `cadence` | `"interleaved"` | When it asks, and how many at once: `interleaved` asks mid-task, one question per quiz (`enforced` mode and quizzes you ask for excepted); `end` waits and asks the remaining budget. |
| `difficulty` | `"auto"` | The tier band: `auto` earns it per project; `easy`/`medium`/`hard` pin it and stop progression. |
| `level_up_after` | `100` | Passing answers needed at the current band, in one project, before it moves up. Answers earned before a promotion are spent. The distinct-concept floor scales with this, so shortening it keeps the runway reachable. |
| `level_up_accuracy` | `0.7` | Minimum accuracy over every answer at that band, not only the passing ones. Declines are excluded from both halves of the fraction. |
| `pass_threshold` | `0.7` | The fraction of a session's required concepts you must answer correctly — grade 3 or better — before the commit gate opens, rounded up. `required` never exceeds `max_questions_per_task`, so at both defaults that is three of four. |
| `max_questions_per_task` | `4` | A budget for the **whole session**, shared between mid-task checkpoints and the end-of-task sweep. Not a batch size — on the default cadence a quiz asks one question, so the budget is spent one at a time or not at all. |
| `min_minutes_between_quizzes` | `20` | Floor between whole quizzes, and the anti-nagging dial for the `end` cadence. It applies in `ambient` mode only — `enforced` ignores it, or a cooldown could make a commit gate unpassable. On `interleaved` nothing it paces exists: every quiz there is one question, so `min_minutes_between_checkpoints` is the dial that applies. |
| `min_minutes_between_checkpoints` | `4` | Floor between single questions on the `interleaved` cadence — both the mid-task checkpoint and the end-of-task sweep. It is what stops eight logged concepts becoming eight questions in a row, and it is what re-arms the sweep, so lowering it asks more often and raising it asks less. `0` asks at every seam; the end-of-task sweep still keeps a one-minute floor, since there this clock is its only loop guard. |
| `max_new_concepts_per_session` | `8` | Cap on concepts Claude may invent per session, against slug sprawl. |
| `max_stop_blocks_per_session` | `3` | Hard backstop on how many times the end-of-task hook may hold a session open. |
| `domains_enabled` | `["*"]` | Restrict questions to named domains. `["*"]` means all. |
| `quiet` | `false` | `true` suppresses the session-start banner and the `eklavya statusline` output. It does **not** stop Eklavya working — concepts are still logged and questions still arrive. Use `mode: off` for that. |

### Setting a namespaced key

`eklavya config set` takes a dotted path, and so does asking in chat:

```bash
eklavya config set memory.capture minimal
eklavya config set retrieval.cross_project true
eklavya config set privacy.exclude_paths "/internal/, /vendor/"
eklavya config set providers.observer null
```

Only the key you name changes; the rest of its namespace is left alone. A list
takes either a comma-separated string or JSON, and a value is read as the type
the setting actually has — so `focus_topic 2` stays the string `"2"` while
`memory.batch_max_events 40` becomes the number `40`.

The one thing that needs JSON is setting a whole object, because there is no
sensible shorthand for one:

```bash
eklavya config set providers.observer '{"kind":"anthropic","model":"<model-id>"}'
```

### The memory namespaces

The keys above are flat because every `.eklavya.json` already written uses them that way. The memory half's keys are nested under six namespaces instead, and they merge the same way: a repo file setting `retrieval.mode` leaves your personal `memory.capture` alone.

#### `memory`

| Key | Default | What it does |
| --- | --- | --- |
| `memory.enabled` | `true` | Whether this project's work is recorded and recalled at all. |
| `memory.capture` | `"full"` | What the capture path accepts. `full` records prompts, tool calls, failures, edits and reads; `minimal` keeps prompts, assistant messages, session seams and notes, and drops the per-file traffic that is most of the volume; `off` stops capture and leaves what is already stored searchable. |
| `memory.batch_max_events` | `40` | Events per observation batch. A session seam flushes whatever is left, so a short session is still summarised. |
| `memory.retention_days` | `null` | Days of raw evidence to keep. Observations built from it survive its deletion. `null` keeps it until you delete it. |

:::note
**`memory.enabled` is independent of `mode`.** `mode: off` means no quizzes, no checkpoints and no gate — it does not mean no history. Someone who silenced the questions did not ask for their project's record to stop, and the reverse (quizzes, no capture) is just as legitimate: that is `memory.enabled: false`.
:::

#### `privacy`

Every entry here is *added* to Eklavya's built-in rules, never replaces them. [Memory](/docs/memory/#what-is-never-captured) lists what the built-in rules already cover.

| Key | Default | What it does |
| --- | --- | --- |
| `privacy.exclude_paths` | `[]` | Extra path fragments that are never captured, on top of the built-in list (`.env`, `/.ssh/`, `.pem`, `credentials.json` and the rest). Matched as a substring of the path. |
| `privacy.exclude_tools` | `[]` | Tool names never captured, when a tool's arguments are usually secrets. |
| `privacy.redact_patterns` | `[]` | Extra regular expressions, applied on top of the built-in secret shapes. A match becomes `[redacted:configured]`. A pattern that does not compile is skipped rather than breaking capture. |

#### `retrieval`

| Key | Default | What it does |
| --- | --- | --- |
| `retrieval.mode` | `"hybrid"` | How memory is searched: `keyword` (FTS5, BM25), `semantic` (cosine over local vectors), or `hybrid` — both, fused. A single search may override it. |
| `retrieval.max_items` | `6` | Entries offered at a session seam before any detail is fetched, and the default `limit` for a search. |
| `retrieval.max_tokens` | `1200` | Estimated-token budget for the whole recalled block, wrapper included. It fills to the budget rather than to `max_items`, because six short notes and six long ones are not the same amount of context. |
| `retrieval.cross_project` | `false` | `true` widens both search and the session-start block to every project on this machine. Off by default: another repository's work is usually noise. |

#### `providers`

Both are `null`, and **nothing turns them on for you** — not an upgrade, not a command. With them unset, the summariser and the embedder are both local and nothing about your code leaves the machine.

| Key | Default | What it does |
| --- | --- | --- |
| `providers.observer` | `null` | A model that writes observation narratives instead of the local extractive summariser. Setting it is the one thing that sends captured work off this machine. |
| `providers.embeddings` | `null` | A model that produces the vectors `semantic` retrieval compares, instead of the local `local-hash-v1` embedder. Each vector records which embedder made it, so two models' vectors are never compared. |

Each takes an object of three fields: `kind` (only `"anthropic"` today), `model`, and `api_key_env` — the **name of the environment variable** holding the key, defaulting to `ANTHROPIC_API_KEY`. The key itself never goes in the config file, because a config file ends up in every export, log line and dashboard payload that prints configuration.

```json title=".eklavya.json"
{
  "providers": {
    "observer": {
      "kind": "anthropic",
      "model": "<model-id>",
      "api_key_env": "ANTHROPIC_API_KEY"
    }
  }
}
```

#### `notifications` — what gets sent out

Off by default, and separately from everything else, because a notification
cannot be recalled: once a session summary is in a team channel, deleting your
local database changes nothing.

| Key | Default | What it does |
| --- | --- | --- |
| `notifications.enabled` | `false` | The master switch. With no sinks configured nothing is sent either way. |
| `notifications.sinks` | `[]` | Where wrap-ups go. Each is an object: `kind` (`"webhook"`, `"command"` or `"file"`), `target`, optional `args` (for `command`), and optional `events` to take only some kinds. |

Two event kinds today: `session_summary` when a session ends, and
`queue_paused` when observation processing has stopped and will not restart by
itself. Every payload goes through the same redaction as capture, and each
event is delivered once however many times the session seam fires.

`command` exists because the interesting integrations are all somebody's
script — a desktop notification, a line in a journal, a message posted by a CLI
that already holds the credentials. The event JSON arrives on the command's
standard input, and no shell is involved, so nothing in `target` is expanded on
the way.

```json title="~/.eklavya/config.json"
{
  "notifications": {
    "enabled": true,
    "sinks": [
      { "kind": "file", "target": "~/eklavya-wrapups.jsonl" },
      { "kind": "command", "target": "/usr/local/bin/notify-me", "events": ["queue_paused"] }
    ]
  }
}
```

#### `sync` — memory across your machines

Off by default. The target is a directory both machines can see — a synced
folder, a mounted share, a git repository — so there is no account and no
service to depend on.

| Key | Default | What it does |
| --- | --- | --- |
| `sync.enabled` | `false` | The master switch. A target alone does nothing, deliberately: a stale path left by a wiped machine should not quietly start publishing. |
| `sync.target` | `null` | The shared directory. Each machine writes its own numbered records into it and reads the others'. |
| `sync.device_id` | `null` | Pin this machine's identity. Normally leave it: an id is minted once and kept in the database, never in a config file, because config files travel and two machines sharing an id would interleave one stream irrecoverably. |

What crosses: memory entries, their tags, and deletions. What never crosses:
your attempts, your mastery, your review schedule, gates, reuse receipts, and
the raw evidence behind an observation. Shared project memory is not shared
learner history.

```bash
eklavya config set sync.target ~/Dropbox/eklavya-sync
eklavya config set sync.enabled true
eklavya memory sync push
eklavya memory sync status
```

Two machines editing the same entry between syncs is a conflict, and a
conflict is **quarantined rather than merged**: your local version stays live,
the incoming one is kept intact, and `eklavya memory sync status` says there is
one to resolve. A deletion propagates as a tombstone and stays deleted — the
machine that still had the entry cannot put it back.

### A complete file

Every key is optional — write only the ones you want to change. This example is a repo file for an onboarding codebase: enforced, grounded in the project, held at easy for everyone.

```json title=".eklavya.json"
{
  "mode": "enforced",
  "focus": "project",
  "cadence": "interleaved",
  "difficulty": "easy",
  "pass_threshold": 0.7,
  "max_questions_per_task": 4,
  "min_minutes_between_checkpoints": 4
}
```

:::tip
**Two settings people misread.** `max_questions_per_task` is a session budget, so turning on `interleaved` moves questions earlier without adding any — and under that cadence it is a ceiling for the session, not a number of questions you will be asked. And `difficulty` is a *band*, not a question — pinning `hard` does not make every question tier 5, it makes tiers 3–5 the range the planner may choose from.
:::

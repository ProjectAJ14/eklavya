For the parts of Eklavya that make sense outside a Claude Code session. `npx eklavya install` already puts it on your machine; to have it on your `PATH` permanently use `npm install -g eklavya`, or run any subcommand without installing via `npx eklavya <command>`. The package ships this one command; the MCP server is `eklavya serve`, not a separate executable.

| Command | What it does |
| --- | --- |
| `eklavya serve` | Runs the MCP server on stdio. This is what Claude Code starts for you — you would only run it by hand to point another MCP client at Eklavya. |
| `eklavya install` | Installs Eklavya into Claude Code: checks Node, installs the runtime and its SQLite driver, registers and enables the plugin, installs the chat skill at `~/.claude/skills/eklavya/`, and creates the database. Safe to re-run — that is how you upgrade, including for a marketplace install, where it pulls the plugin's git clone forward. |
| `eklavya uninstall [--purge]` | Removes the plugin, the runtime and the chat skill, and deregisters it from Claude Code. Your learning history is kept unless you pass `--purge`. |
| `eklavya config get` | Prints the effective configuration as JSON, plus the paths of the global and repo files it came from. |
| `eklavya config set <key> <value>` | Changes one setting. Add `--repo` to write `.eklavya.json` at the repository root instead of your global config. Add `--topic <topic>` when setting `focus learn`. |
| `eklavya doctor` | Checks that everything is wired up: the runtime, the SQLite driver, the plugin's registration with Claude Code, the chat skill, then the database, counts, journal mode, this project's level and runway, and the effective mode, focus and cadence. It also **applies your [concept packs](/docs/packs/)** — the only command that does so unconditionally — and names any that failed to load. Exits non-zero if a check fails, and names the command that repairs it; a broken pack is reported but does not fail the run, because `eklavya install` cannot repair one. |
| `eklavya dashboard [--port <n>] [--no-open]` | Serves your learning history as a local web page and opens it in your browser. `--no-open` serves it and prints the URL instead. See [The dashboard](/docs/dashboard/). |
| `eklavya statusline` | Prints your dials as one line for a status bar, or nothing at all. See [below](#eklavya-statusline). |
| `eklavya memory <sub>` | Drives the memory half from a terminal: `status`, `search`, `timeline`, `show`, `process`, `prune`, `import`, `export` and `restore`. See [below](#eklavya-memory). |
| `eklavya db-path` | Prints the database location. Useful in scripts. |
| `eklavya export-rules [--out <file>]` | Writes the tutor pedagogy out as a Markdown rules file, for editors that read one. Claude Code loads the pedagogy in pieces, on demand; a rules file is a single always-applied document, so every piece is inlined into it. With no `--out` it prints to stdout. Nothing in the Claude Code flow needs it. |

### `eklavya memory`

The memory half, for a terminal. Inside a Claude Code session the MCP tools
are better — they scope to the project on their own — but these work anywhere,
and two of them have no equivalent as a tool.

| Subcommand | What it does |
| --- | --- |
| `status` | Is capture healthy: entries, evidence waiting to be summarised, the job queue, whether a provider is configured, spool drops, and the reuse totals with the saving or overhead spelled out. This is the command for *"why does Eklavya remember nothing?"* — it tells apart switched off, queued, a provider refusing, and evidence dropped while the database was unreachable. |
| `search <query>` | `--mode keyword\|semantic\|hybrid`, `--limit`, `--all-projects`. Titles and ids, not narratives. |
| `timeline` | Recent entries, newest first. `--limit`, `--since <iso date>`. |
| `show <id>` | One entry in full, with the raw evidence it was built from. |
| `process` | Drains the observation queue now, rather than waiting for the next session seam. `--max <n>`. |
| `prune` | Deletes raw evidence older than `memory.retention_days`, keeping the observations built from it. Does nothing when retention is unset. |
| `import <source.db>` | Imports a Claude Mem database. See below. |
| `export <file>` | A versioned JSON file of entries, tags, evidence links and receipts. |
| `restore <file>` | Reads that file back in. See below. |

`export` and `restore` are one pair: the file is your backup, and `restore` is
how you undo. Take an export before anything irreversible — an import, a
version upgrade, a `--purge` — and if it goes wrong, restore it.

```bash
eklavya memory export ~/eklavya-backup.json
eklavya memory restore ~/eklavya-backup.json
```

A restore is **additive and idempotent**: it adds what is missing, matches what
is already there by identity rather than by row number, and running it twice
adds nothing the second time. It never writes an attempt, a mastery row or a
gate — restoring memory cannot alter what you have been assessed on. It rebuilds
the search index and the embeddings for everything it brought back, so restored
entries are findable immediately. A file written by a newer version stops with
the version it found and the version this build understands, rather than
guessing at a shape it has never seen.

#### Importing an existing Claude Mem history

```bash
eklavya memory import ~/.claude-mem/claude-mem.db --dry-run
eklavya memory import ~/.claude-mem/claude-mem.db --map-here eklavya
```

The dry run is worth doing first. It opens the source **read-only**, prints the
schema version, the row counts, the projects it found, and a field-by-field
report of what maps where, what is deliberately dropped and why, and which
columns the importer has never seen — and writes nothing.

Three things worth knowing before the real run:

- **It never touches your learning history.** Imported observations arrive
  unassessed. Concepts the source had attached become candidates, not concepts:
  no mastery, no attempts, no gate is affected.
- **It maps projects only when you tell it to.** Claude Mem names a project
  with a bare string; Eklavya keys one by the checkout's absolute path.
  `--map-here <name>` files that source project under the checkout you are
  standing in, and `--map <name>=<path>` under any other. Anything left
  unmapped is still imported, and still searchable — but only with
  `--all-projects`, and the report says which names those were.
- **It is resumable and it does not duplicate.** Run it twice and the second
  run imports nothing. `--resume` reuses the snapshot an interrupted run left
  rather than copying the source again.

A source database newer than this importer understands stops with the version
it found and the version supported, rather than guessing at a schema it has
never seen.

### `eklavya statusline`

Your four dials, in Claude Code's status bar, so the settings that shape a
question are on screen when it arrives:

```text
~/eklavya · main · Opus 5 · [EKLAVYA ambient · concept · interleaved · easy]
```

`eklavya install` sets this up for you, **but only into an empty slot**.
`statusLine` holds one command, so installing ours and keeping yours cannot
both happen, and between the two, yours wins: a status bar is a thing people
build deliberately. If you already have one, nothing is touched and the block
below is the manual route.

```json title="~/.claude/settings.json"
{
  "statusLine": {
    "type": "command",
    "command": "eklavya statusline"
  }
}
```

Already have a status line and want both? Call `eklavya statusline` from your
own script and append the output — it prints one line and exits 0, and prints
nothing when it has nothing to say. An uninstall removes the line only when it
is exactly the one the installer wrote, so a composed one survives.

This is a terminal feature. The Claude Desktop app has no status bar to run it
in, so the dials are not on screen there; questions there are signed with an
`[Eklavya]` line above the stem instead, and [the dashboard](/docs/dashboard/)
carries the settings.

It stays silent when `mode` is `off`, when `quiet` is `true`, or when you have
turned Eklavya off for this session, so a bar you have stopped reading is a bar
Eklavya is not writing to. `enforced` mode is printed in amber, because that is
the one dial value with a consequence attached: your commits are gated. Pass
`--no-color`, or set `NO_COLOR`, for plain text.

The bar never shows the tier of the question in front of you. A status bar
refreshes when Claude Code decides to, not when a question appears, so a tier
there would sometimes name the previous question's difficulty. The level is
there instead, and it is the part that explains the pitch — `easy` means tiers
1–2. For the exact tier of any past answer, see [the
dashboard](/docs/dashboard/).

### What `doctor` looks like

```bash
$ eklavya doctor
home:     /Users/you/.eklavya
runtime:  /Users/you/.eklavya/runtime
driver:   better-sqlite3 loads on Node 22.14.0
plugin:   /Users/you/.claude/plugins/marketplaces/eklavya — registered, enabled
skill:    /Users/you/.claude/skills/eklavya
database: /Users/you/.eklavya/knowledge.db
concepts: 87
attempts: 41
mastered: 12
journal:  wal
level:    easy (23/100 passing answers in /Users/you/code/api)
mode:     ambient
focus:    concept
cadence:  interleaved (one question mid-task, min 4m apart)
```

This is the first thing to run when something feels wrong.

The first four lines are the install itself. They matter because Eklavya fails
quietly by design — every hook exits successfully whatever happens, so it can
never break a session you are in the middle of. The cost of that guarantee is
that a broken install looks exactly like a quiet one: Eklavya simply stops
asking. These four checks are the only place that says which it is.

When one fails, `doctor` says so and names the fix:

```bash
$ eklavya doctor
home:     /Users/you/.eklavya
runtime:  /Users/you/.eklavya/runtime
driver:   FAILED — will not load on Node 24.0.0 — Error: dlopen: symbol not found
plugin:   /Users/you/.claude/plugins/marketplaces/eklavya — registered, enabled
skill:    /Users/you/.claude/skills/eklavya
...

Something is broken. Run: eklavya install
```

`eklavya install` is the repair for all four. It is idempotent — re-running it
reinstalls the runtime, re-copies the plugin and rewrites the registration,
leaving your learning history untouched. `doctor` never repairs anything itself;
it reports, and you decide.

| Check | What it means when it fails |
|---|---|
| `runtime` | The compiled server is missing from `~/.eklavya/runtime`. Usually an install that was interrupted. |
| `driver` | The SQLite driver will not load — almost always a Node upgrade that left the prebuilt binary on the wrong ABI. |
| `plugin` | The plugin is gone from Claude Code's registry, or is registered but switched off in `settings.json`. |
| `skill` | The chat skill is missing from `~/.claude/skills/eklavya`. If the name is taken by a skill of your own, `doctor` says so and leaves it alone — move yours first. |

:::note
**Guard rails you will meet.** `config set` rejects unknown keys and lists the valid ones. `focus learn` without `--topic` is refused outright, because that combination produces no questions at all. `--repo` outside a git repository is refused, because there is nowhere to write the file.
:::

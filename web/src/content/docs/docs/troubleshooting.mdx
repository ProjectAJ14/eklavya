Start with `eklavya doctor`. It answers most of these in one screen, and it
checks the install itself — the runtime, the SQLite driver, the plugin's
registration and the chat skill — before anything else. If one of those has
broken, `doctor` says which and tells you to run `eklavya install`, which is
idempotent and repairs all four without touching your history.

That first block matters more than it looks. Eklavya never breaks a session:
every hook exits successfully whatever happens. So a broken install and a quiet
one look identical from the inside — it just stops asking. `doctor` is the only
thing that tells them apart.

| Symptom | Likely cause and fix |
| --- | --- |
| No greeting at session start | Either `quiet` is `true`, the runtime is not installed yet, or the plugin did not load. Run `/plugin` and check for errors, then `eklavya doctor`. If you installed through the marketplace, `npx eklavya install` finishes the runtime immediately. |
| No questions at all, ever | Check the mode is not `off`. Then check that Claude is actually logging concepts — with nothing logged there is nothing grounded to ask about. `/eklavya:quiz` will tell you which of the two it is. |
| Nothing at all in a long session, and nothing was ever logged | The instruction to log concepts is injected once, at session start, so in a long session it can end up buried under everything that came after it. Eklavya notices this particular case: after about twelve minutes of a session that has logged **nothing**, it restates the instruction in one line — at most once every twenty-five minutes, and at most three times before it gives up, because a session that logs nothing is also what an unreachable server looks like. Resuming a session or compacting one starts that count again, since the original instruction is reprinted then too. `quiz.enabled: false` is what switches the reminder off; `quiet` does not, because the reminder is context for Claude rather than output for you. |
| Questions arrived earlier in the session, then stopped | This is the other case, and no reminder fires for it — concepts are logged per task, and a task can legitimately run a long time, so Eklavya cannot tell a quiet stretch from a long one. Ask Claude directly to log what the current task touched, or run `/eklavya:quiz`. |
| Questions only arrive at the end, or several in a row | Cadence is `end`. `eklavya config set cadence interleaved` — that asks at the seam where a concept is logged, and caps a quiz at one question. If they still arrive late on `interleaved`, Claude is logging concepts at the end of the task rather than as it works; tell it to log as it goes. |
| Too many interruptions | Raise `min_minutes_between_checkpoints` — on `interleaved` it paces both the mid-task question and the end-of-task sweep — or lower `max_questions_per_task`. Switching to `end` is the blunt version. |
| Questions feel far too easy | You are on `easy`, which is where every project starts. Run `/eklavya:level` to see the runway — you may be close to a promotion. Pin a band only if you are sure. |
| My global setting stopped applying | Your own settings for this project are overriding it. The session banner names which ones; `eklavya config get` prints the file path under `~/.eklavya/projects/`. |
| The database file does not exist | The MCP server never started. Check `/plugin` for errors and confirm `node --version` is 22 or newer — below that the native database binding has no prebuilt binary and will not install. |
| Lots of `claude` or `node` processes, or the machine slows down, with a memory model configured | That was the 1.24.0 bug: every summariser run started another worker. First set `providers.observer` to `null` so nothing new starts, then run `eklavya memory stop`. Upgrade with `npm install -g eklavya@latest && eklavya install` — the plugin can update itself while the runtime under `~/.eklavya/runtime` stays on the old version, and the old runtime is the one that loops — and check `eklavya memory status`: the `worker:` line should show at most one pid. A worker left over from 1.24.0 never recorded itself, so `memory stop` can't see it; end those by hand (`pkill -f 'memory process'`) or restart. Before turning the model back on, run `eklavya memory backlog`: batches marked as observer helper sessions are the loop's own noise, and `eklavya memory backlog discard --helpers` (or `quarantine --helpers`, to keep them) stops the model spending your subscription summarising them. |
| Eklavya remembers nothing about this project | Four different problems look identical from the outside, and `eklavya memory status` tells them apart: `enabled: false` or `capture: off` means it is switched off; entries at zero with pending evidence above it means nothing has summarised yet, and `eklavya memory process` drains it; `queue.paused` means a configured provider is refusing, with `error_class` saying whether that is auth, quota or missing — log in to Claude Code, wait out the usage limit, or put `claude` on the PATH Claude Code starts with (launched from an app or IDE, it is often shorter than your shell's), then run `eklavya memory process`, which is what puts paused jobs back in the queue, since nothing automatic will; and `dropped_events` above zero means the spool overflowed while the database was unreachable — that evidence is gone. |
| A search finds nothing, but I know it happened | Three possibilities in order. It may be in another project: Eklavya scopes to this checkout, so add `--all-projects`. It may have been imported and never placed — `eklavya memory status` counts those as `unplaced`, and re-running `eklavya memory import` on `~/.claude-mem.retired/claude-mem.db` (with `--map-here` for any name the transcripts cannot place) moves them to their checkout without duplicating anything. Or you write in Japanese or Chinese: the full-text tokenizer has no word boundaries for unspaced scripts, so a whole title becomes one token and `retrieval.mode: keyword` finds almost none of it. Set it back to `hybrid`, which measures 0.533 top-1 against keyword's 0.200 on the CJK half of the retrieval eval — better, but still missing nearly half, so search by a filename or an identifier where you can. Those are Latin script whatever the prose around them is, and they are what actually bridges the two. |
| My savings percentage says "unavailable" or shows overhead | Both are honest answers rather than faults. "Unavailable" means no reuse has been *confirmed* delivered yet, and a number would be invented. Overhead means the recalled block cost more tokens than reading the underlying evidence would have — which happens on a small corpus, where an observation is longer than the tool call it summarises, and stops happening as the history grows. Eklavya reports it rather than clamping it to zero. |
| Memory recorded something I did not want recorded | `memory_delete` removes an entry, and `privacy.exclude_paths`, `privacy.exclude_tools` and `privacy.redact_patterns` stop the next one. If a secret got through, please [open an issue](https://github.com/ProjectAJ14/eklavya/issues) with the *shape* of it and never the value — the built-in patterns are a list that only grows by someone hitting a gap. |
| A commit is blocked and I do not know why | `/eklavya:gate` tells you how many concepts are outstanding. `/eklavya:quiz` clears it. |
| Commits are blocked but I never turned on the gate | Your project settings have `quiz.enforced`. Run `eklavya config get` for the file path, then `eklavya config set quiz.enforced false --project`. Since settings are per developer, nobody else can have turned this on for you — an older committed `.eklavya.json` may have been migrated into your config on a previous session. |
| Memory is off and I never turned it off | You kept Claude Mem when `eklavya install` asked, or the installer ran without a terminal and made that choice for you. Run `eklavya install --memory eklavya` to import Claude Mem's history and switch over. |
| Questions stopped and I assumed everything had | `quiz.enabled: false` stops the questions and nothing else — memory keeps recording, and `eklavya memory status` proves it. Session start says which half is off. The two are separate switches on purpose. |
| The gate never holds, though the repo says enforced | Check for `quiz.enabled: false` in the same file. A gate needs passed questions and nothing would ask any, so the enforcement is ignored rather than blocking every commit for ever. `eklavya doctor` reports this combination by name. |
| The git hook does not fire | It only acts on projects whose config sets `quiz.enforced` (or the retired `"mode": "enforced"`), and it deliberately fails open when `jq` or `sqlite3` is missing. Check both. |
| An `.eklavya.json` vanished from my checkout | Eklavya moved it. Settings no longer live in repositories, so the next session there lifted it into `~/.eklavya/projects/<checkout>/config.json`, keeping every setting, and deleted it. `eklavya config get` shows where it went. |
| Eklavya worked, then went silent after a Node upgrade | The SQLite driver's prebuilt binary is tied to a Node ABI. `eklavya doctor` reports this as `driver: FAILED`; `eklavya install` rebuilds it. |
| `doctor` says the plugin is registered but not enabled | Under `enabledPlugins` in `~/.claude/settings.json`, `eklavya@eklavya` is `false` or missing entirely. Re-enable it there, with `/plugin` in Claude Code, or by running `eklavya install`. |
| `doctor` says the skill is a different skill named eklavya | You have your own `~/.claude/skills/eklavya/`. Eklavya will not overwrite it — rename or move yours, then run `eklavya install`. |
| Questions in Claude Desktop have no **Eklavya** header | Expected, and handled. The header is a chip Claude Code draws in a terminal; the Claude Desktop app draws a question card with no chip in it, and no plugin can change that. Questions there open with `[Eklavya]` on their own line instead. If you see *neither* the chip nor that line, the question did not come from Eklavya. |
| It works in the terminal but not in Cowork | Cowork keeps a separate list of plugins and `doctor` cannot see it, so a clean report says nothing about Cowork. Install it there: **Customize → Plugins → Add marketplace → `ProjectAJ14/eklavya`**. |
| Cowork questions talk about code, but I am not writing code | Eklavya recognises a Cowork session from the entrypoint the app sets, and re-points its wording at the work you produced. If it did not, the app used an entrypoint this version does not know — that is a bug, so please [open an issue](https://github.com/ProjectAJ14/eklavya/issues) naming your Claude Desktop version. `EKLAVYA_SURFACE` will not help here: Claude Desktop composes the environment for the hooks and the server itself, so there is no shell of yours for them to inherit it from. |
| Commits are not blocked in Cowork | Correct, and the session banner says so. The gate holds `git commit`, and Cowork does not commit. The questions still arrive. |
| Nothing works in Cowork, and your organisation manages Claude Desktop | Two administrator settings switch Eklavya off there, both silently. A full-VM Cowork sandbox moves the session off your machine and away from `~/.eklavya/runtime`; `isLocalDevMcpEnabled: false` refuses local MCP servers outright. Ask your administrator which is set. |
